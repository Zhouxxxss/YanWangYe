ARCHITECTURE  ·  TECH STACK  ·  FEASIBILITY

研王爷 · 考研伴学系统 基于 Spring Boot + React 的前后端分离技术方案

一期聚焦「学习管理 · 错题 Anki · 计划模板 · RAG 溯源答疑 · 背诵打卡 · 数据大盘」个人备考闭环，前端采用动态强交互风格；二期通过预留接口接入社区、搭子小组与择校库。

后端：Spring Boot · Spring Security · JWT · Redis 前端：React · TypeScript · Framer Motion · 强交互 AI：RAG · 大模型 · 向量检索 分期：一期闭环交付 · 二期接口预留

01可行性分析

从技术、业务、数据、进度、风险五个维度对「研王爷」落地可行性进行评估，并给出建议的 MVP 收敛范围。

● 技术可行性 —— 高
一次 Spring Boot 3 + React 18 前后端分离，技术栈均为业界成熟方案，关键难点均有成熟组件与算法支撑：
· 权限：Spring Security + JWT + Redis 组合非常成熟，五表 RBAC 标准化
· 定时/限流：Redis 原生支持过期事件 + 定时任务
· Anki 间隔重复：SM-2 算法为标准算法，可直接按公式实现
核心熟练度风险点集中在 RAG 与 LLM 集成。
● 业务可行性 —— 高
痛点密集且明确：规划混乱、复习无闭环、错题复盘无规律、答疑低效、择校无参考。垂直场景壁垒高于通用学习 APP，差异化明显。闭环设计完整（规划→执行→复盘→答疑→沉淀→协作），变现链路清晰（会员/题库/模板）。

五大维度评估表

维度结论评估说明
技术可行性良好核心均为成熟技术（Spring Security/JWT/Redis/SM-2/RAG）。真正需要投入测试的是「AI 问答」链路，需预留 API 密钥与向量库接入。
业务可行性良好垂直考研场景，需求真实且高频（每日学习/刷题/复盘），非伪需求。模块间强耦合设计形成完整闭环，正是产品护城河。
数据可行性中等院校库、复习模板等「冷启动数据」需要人工采集清洗，工作量大且有版权/准确性风险。RAG 问答效果依赖语料质量。
进度可行性良好一期范围已锁定且以复用模块为主，可分步交付。一期跑通「学习+错题+背诵+答疑+统计」个人闭环，二期以预留接口接入社区/小组/择校，无返工风险。
合规可行性中等社区内容需审核（文档已验证管理员公共文档审核机制）、AI 生成内容需标识、院校资料需注意版权、用户隐私（学习数据）需按《个人信息保护法》处理。

风险与应对

AI 依赖
中高
  • 风险：RAG 溯源准确率依赖模型与提示词；模型 API 有成本与可用性。
  • 应对：抽象统一的 AIProvider 接口（可切换模型商）；落地「RAG 溯源引用」降低幻觉；对大模型调用做限流+缓存+配额。
冷启动数据
中高
  • 应对：院校库采用「UGC + 官方模板内置 + 抓取人工校验」三种来源逐步补齐；先内置数量有限的官方复习模板支撑 MVP。
并发与性能
中低
  • 应对：单体起步 + Redis 做缓存/限流/定时，读多写少数据引入 Elasticsearch，必要时再拆微服务与 MQ 削峰。
安全合规
中低
  • 应对：复用现有五表角色权限 + 数据权限；公共文档审核；AI 输出标识；敏感数据加密与脱敏。

一期交付范围（已锁定）

一期交付：账号权限（已有）→ 学习计时/日程（已有）→ 错题本 + Anki → 计划模板导入 → RAG 溯源答疑 → 背诵打卡 → 数据大盘。二期通过预留接口接入：社区互助、搭子小组、择校库，一期不实现但接口与表结构先留好，避免返工。

结论

整体可行性：中等偏高，建议推进。 项目技术栈扎实、业务闭环完整、迭代节奏清晰，作为个人项目或创业产品的可落地性良好。最大的前置成本和不确定性在于「冷启动数据」与「AI 效果」，建议通过 MVP + 可切换 AI Provider + 数据分批注入 三大策略降低风险。

Redis 的核心职责

职责Key 设计示意说明
会话管控login:token:<uid>JWT 黑名单/主动下线，Redis 存储会话有效状态。
Anki 复习周期anki:due:<date>:<uid>SM-2 到期任务集合（错题 + 背诵卡片共用调度器），配合定时任务推送「今日待复习」。
限流 + 缓存rate:<uid>:<api> / cache:<key>对 AI 调用、发帖等做限流；热点数据(择校/模板)缓存。

分布式锁用 SETNX，避免重复复习/重复任务生成。既能支撑定时推送，也天然适配未来多实例部署。

设计提醒：RAG 检索范围必须融入「数据权限」——同一文档，公共可见、组织可见、仅本人可见；向量检索在召回阶段即按用户可见范围过滤，避免越权查阅他人资料。

关键技术实现要点

  • Anki 算法：采用标准 SM-2 间隔重复算法，按 4 个质量评分档位计算下次复习日；错题与背诵卡片共用一套复习调度器（抽象 ReviewItem 接口），复习调度落地 Redis 待复习集合。
  • 背诵打卡：recite_card 录入后由大模型生成抽背问题池（Prompt 预生成缓存，避免每次实时调用）；默写对比走 LLM 相似度判定，打卡成功发布 CheckinEvent 计入学习时长。
  • 数据大盘性能：study_stat_daily 由定时任务预聚合（签到/时长/任务完成率/错题复盘），大盘读预聚合表 + Redis 缓存，避免实时全表扫描；热力图与占比图支持周/月切换。
  • 前端强交互：计时器/番茄钟用 Zustand + requestAnimationFrame 驱动倒计时（避免 setInterval 漂移）；打卡/完成日程走 TanStack Query 乐观更新；AI 回答 SSE 流式渲染打字机效果；动效统一 Framer Motion 编排。
  • AI 可切换：定义 AIChatClient / EmbeddingClient 接口，适配不同推理服务商；统一 Prompt 模板（章节讲解/错因分析/抽背出题）。
  • 溯源引用：LLM 返回的引用段落保留 doc_id + 段落位置，前端渲染可点击跳转原文。
  • 配额管控：按角色维护 doc_quota，在文档上传、向量入库两处做存储上限与单文件大小校验。
上线建议：第一版以前后端单体 + Nginx 部署于单台云服务器即可（Docker Compose 编排 MySQL/Redis/后端/前端），成本低、易维护；待注册量与数据量上来后再评估 ES、消息队列与微服务化。
